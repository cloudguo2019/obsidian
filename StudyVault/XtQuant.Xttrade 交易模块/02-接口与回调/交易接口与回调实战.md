# 交易接口与回调实战

## 接口分层

| 层级 | 接口 | 核心作用 |
| --- | --- | --- |
| 连接层 | `start` `connect` `stop` `run_forever` | 启动线程、连接、阻塞等待 |
| 订阅层 | `subscribe` `unsubscribe` | 开关主推消息 |
| 交易层 | `order_stock` `order_stock_async` `cancel_order_stock` | 下单与撤单 |
| 查询层 | `query_stock_asset` `query_stock_orders` `query_stock_trades` `query_stock_positions` | 拉取账户与交易状态 |
| 信用层 | `query_credit_detail` `query_stk_compacts` 等 | 信用账户特有查询 |
| 扩展层 | `export_data` `query_data` `sync_transaction_from_external` | 通用数据导出/查询与外部成交导入 |

## 1) 同步与异步下单

### 同步下单 `order_stock`

- 返回值是 `order_id`（>0 表示成功）。
- 适合流程简单、对返回时延不敏感的策略。

### 异步下单 `order_stock_async`

- 返回值是请求序号 `seq`。
- 后续需要在 `on_order_stock_async_response` 里对齐 `seq` 与 `order_id`。

> [!tip]
> 推荐在策略状态中维护一个 `pending_seq -> intent` 映射，回调到来后再完成状态落账。

## 2) 撤单接口

- `cancel_order_stock(account, order_id)`：按本地订单号撤单。
- `cancel_order_stock_sysid(account, market, code, sysid)`：按柜台合同号撤单。
- 同步与异步撤单接口都存在，使用时保持策略内一致。

## 3) 查询接口使用原则

1. `query_stock_order` / `query_stock_orders`：分别用于单笔追踪和全量快照。
2. `query_stock_trades`：用于成交回填，和 `on_stock_trade` 配合。
3. `query_stock_positions` / `query_stock_position`：用于仓位核对与风控。

> [!warning]
> 查询返回 `None` 可能表示失败，也可能表示当日无数据，要结合日志和账户状态判断。

## 4) 回调驱动策略的最小闭环

```text
下单意图产生
  -> order_stock/order_stock_async
  -> on_stock_order (委托状态变化)
  -> on_stock_trade (成交变化)
  -> on_order_error/on_cancel_error (失败补偿)
  -> query_stock_orders/query_stock_positions (兜底对账)
```

## 5) 宽松时序（relaxed response order）理解

文档提到可开启专用线程返回主动请求结果，以避免在推送回调里同步查询造成卡住。

```text
t1 push1
t2 push2
t3 push3
t4 resp(query from t1 callback)
```

- 关闭时：`resp` 常排队在推送后处理，可能卡回调逻辑。
- 开启时：`resp` 可更早返回，但时间先后可能与推送顺序不一致。

> [!important]
> 如果策略对时序非常敏感，优先使用异步查询接口，避免在推送回调里做阻塞同步查询。

## 6) 回调清单（必会）

| 回调 | 含义 |
| --- | --- |
| `on_disconnected` | 连接断开 |
| `on_account_status` | 账户状态变化 |
| `on_stock_order` | 委托状态变化 |
| `on_stock_trade` | 成交变化 |
| `on_order_error` | 下单失败 |
| `on_cancel_error` | 撤单失败 |
| `on_order_stock_async_response` | 异步下单响应 |
| `on_smt_appointment_async_response` | 约券异步响应 |
